## Key Judgment Call: Build In-App Alerting, or Integrate PagerDuty?

`[INFERENCE, the central open question this analysis surfaces]`: DataSentinel's brief describes an **in-app** Alerts/Incidents experience (severity, grouping, escalation, suppression *within the DataSentinel UI itself* — `UI_UX_RESEARCH.md` §9), not an integration with an external on-call tool. The PagerDuty skill family is the best-covered, most mature part of this entire skill landscape — but installing it only pays off if DataSentinel's actual escalation path routes through PagerDuty (or a similar tool) rather than staying self-contained.

**Recommendation:** treat the PagerDuty skills' **design patterns** (dedup keys, alert grouping, escalation-policy structure) as reference material now — read them, borrow the grouping/dedup logic for `DATASENTINEL_DESIGN_SYSTEM.md`'s Alerts component — but **do not install/integrate PagerDuty itself** until there's an explicit decision that DataSentinel needs external on-call routing rather than in-app incident tracking. This keeps the "avoid unnecessary infrastructure" principle intact while still capturing the real design value these skills offer.
