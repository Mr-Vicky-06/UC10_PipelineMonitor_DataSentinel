# PHASE 7 BASELINE AUDIT
**Date:** August 2026
**Objective:** Assess the current state of DataSentinel's frontend architecture before executing the Phase 7 soft reboot.

## 1. Frontend Architecture & Pages
- **Operations Center (`/page.tsx`)**: Currently heavily chart-centric. Displays KPI metrics and a large VolumeChart. Lacks a clear pipeline lifecycle topology.
- **Pipeline Runs (`/pipelines`)**: Generic tabular list. Shows runs but doesn't immediately visually highlight failure stages intuitively.
- **Data Quality (`/data-quality`)**: Displays DQ violations, but has excessive empty space if no violations occur.
- **ML Anomalies (`/anomalies`)**: Displays feature/volume anomalies, but empty state lacks semantic context (is ML offline, or are there truly no anomalies?).
- **Incidents (`/incidents`)**: Successfully integrated with the FastAPI Alert Engine. Real data is flowing.
- **Analytics (`/analytics`)**: Currently just an embedded chart/Grafana placeholder with a basic Recharts block. Underutilized.

## 2. API Routes & Backend Contracts
- **`api/alerts`**: Proxies requests cleanly to the real `alert-engine` FastAPI service (port 8000). Working correctly.
- **`api/pipelines`**: Reads directly from `pipeline_telemetry.duckdb`. Operational.
- **`api/data-quality`**: Reads from DQ outputs.
- **`api/anomalies`**: Reads from `anomaly_events.parquet`.

## 3. Real-Time Capabilities
- Next.js Server Components / React Query: The hooks currently utilize a 30-second refetch interval (`cache: 'no-store'`).
- The Alert Engine FastAPI exposes a WebSocket endpoint `/ws/alerts`, but the UI is currently polling instead of connecting to the socket.

## 4. Current UI Problems & Runtime Errors
- **React DOM Warning**: `Warning: React does not recognize the trendValue prop on a DOM element.` Caused by `<MetricCard trendValue="...">` spreading unknown props to a `div` via `<Card {...props}>`.
- **Chart Aggregation**: The `VolumeChart` aggregates pipeline counts poorly, resulting in a single massive 1,000k spike that hides recent granular telemetry.
- **Incident Investigation UX**: Currently requires manual clicking around. The connection from Incident → Pipeline → SLA → RCA is disconnected.
- **SLA Visualization**: Buried or non-existent. "AT RISK" status is not prominent.
- **Empty States**: Not semantically distinct. Needs differentiation between `NO DATA`, `STALE DATA`, `AWAITING TELEMETRY`, and `SERVICE UNAVAILABLE`.

## 5. Contract Audit & Integration Flaws Discovered

During the Checkpoint 1 Baseline & Contract Audit, several critical integration flaws were discovered which silently break the UI's operational reality without crashing:

### A. Pipeline Lifecycle (`api/pipelines`)
**Flaw:** Historical pipeline runs appear as `STARTED` in the UI despite being successfully completed or failed in the backend.
**Root Cause:** The `pipeline_telemetry.duckdb` table (`pipeline_events`) contains 3,274 `STARTED`, 3,187 `COMPLETED`, and 58 `FAILED` events. The Next.js API query groups by `run_id` and incorrectly selects `MAX(status)`. Because "S" comes after "C" and "F" alphabetically, `STARTED` always wins the `MAX()` aggregation, falsely reporting completed runs as still started.
**Resolution:** The SQL query must use a conditional aggregation or window function (e.g., `arg_max(status, timestamp)`) to get the true latest status.

### B. Data Quality (`api/data-quality`)
**Flaw:** The UI reports "No DQ violations found."
**Root Cause:** The authoritative backend file `outputs/anomaly/dq_results.parquet` is completely empty (0 rows). The Next.js API correctly reads it and returns `[]`. 
**Resolution:** The UI is correctly reflecting the backend state. There is no frontend bug here. We must not invent fake DQ violations.

### C. ML Anomalies (`api/anomalies`)
**Flaw:** The UI reports 0 ML Anomalies despite the backend generating them.
**Root Cause:** `outputs/anomaly/anomaly_events.parquet` actually contains **2,082** anomaly records. However, the Next.js API query attempts to `ORDER BY detected_at DESC`. The column `detected_at` does not exist in the parquet schema (it is named `window_date`). DuckDB throws a Binder Error, and the API silently catches it and returns `[]`.
**Resolution:** Fix the API route to query `ORDER BY window_date DESC` and correctly map the backend schema (which contains `isolation_forest_flag`, `anomaly_type`, `severity`, etc.) to the frontend `AnomalyEvent` interface.

### D. SLA Engine & Visibility
**Flaw:** SLA status is completely hidden or shows "UNKNOWN" in the Incident UI.
**Root Cause:** SLA violations correctly fire as `SLA` events into the Alert Engine, but the frontend's API adapter explicitly mapped `sla_status: 'UNKNOWN'` for all alerts. Additionally, the SLA ETA and throughput metrics generated by the backend are dropped before they reach the UI because the frontend's `AlertEvent` schema does not natively accept them.
**Resolution:** The Next.js API adapter must dynamically extract SLA metrics from the Alert Engine's `EvidencePack` or detailed response, mapping them into standard SLA fields (`sla_status`, `eta`, `required_throughput`) for the UI to consume. We will NOT write an SLA calculator in React; we will strictly surface the backend's math.

### E. Incidents (`api/alerts`)
**Flaw:** The UI historically hardcoded some UI identities or failed to deduplicate properly.
**Root Cause:** The previous static JSONL file lacked true identity tracking.
**Resolution:** FIXED in Phase 6.7. The UI now natively maps `incident_id` 1:1 to the real `alert_id` from the FastAPI Alert Engine. Deduplication is handled internally by the ActionEngine (incrementing `occurrence_count`), which perfectly propagates to the UI. The contract here is sound, but the UI investigation screen needs restructuring (Master → Detail) to link the `alert_id` to its root RCA.

## 6. Grafana Analytics
- Missing deep integration. Currently, it acts as a secondary thought rather than the authoritative source for deep historical operational analytics.

## 7. Security & Stability
- Secrets (Gemini, Sendgrid) are properly sequestered in server-side `.env`.
- No backend logic needs to be rewritten; the DataSentinel engine is solid. The sole focus must be frontend observability, design coherence, and E2E connectivity.
